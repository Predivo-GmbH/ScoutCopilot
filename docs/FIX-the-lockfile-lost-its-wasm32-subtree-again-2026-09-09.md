# FIX — master could not be installed anywhere except the Windows machine that edited its lockfile

**Date:** 2026-09-09 · **Board row:** `monitor-scoutcopilot-ff4b4a1c` · **Session:** wave6-A

## What was wrong

Every Linux install of `master` died before it ran a line of our code:

```
npm error `npm ci` can only install packages when your package.json and package-lock.json … are in sync.
npm error Missing: @emnapi/core@1.11.3 from lock file
npm error Missing: @emnapi/wasi-threads@1.2.3 from lock file
```

Dead at the install step, all on `master`: Critical Path Tests
[34396326463](https://github.com/Predivo-GmbH/ScoutCopilot/actions/runs/34396326463) (`6997a6d`),
[34395892700](https://github.com/Predivo-GmbH/ScoutCopilot/actions/runs/34395892700) (`2494816`),
Deploy to Staging 34386899296, and regen-lock 34387060702.

`node_modules/@tailwindcss/oxide-wasm32-wasi` declares `@emnapi/core: ^1.11.1`, and nothing in the
lockfile provided it. The entry was pruned by commit `99222ad` — an `npm audit fix
--package-lock-only` run **on Windows** to clear the two HIGH advisories that had failed the
12:02Z promotion. That commit did what it was asked; it also silently deleted the parts of an
OPTIONAL platform subtree the local machine would never install.

## Why it is not a one-off, and why it cannot be fixed on Windows

Measured on the work PC at 19:58Z on a clean checkout of `origin/master`: a plain

```
npm install --package-lock-only --ignore-scripts
```

reported **"up to date"** and *deleted a further 11 lines* — `node_modules/@emnapi/runtime` — rather
than repairing the two entries that were missing. Windows npm prunes this subtree on every
lockfile-editing command. Repairing this lockfile from Windows is not possible, in any incantation.

`.github/workflows/regen-lock.yml` exists precisely to do the repair on Linux — and it could not.
Its verification step was `npm ci --dry-run`, which crashes inside npm itself with `Cannot read
properties of null (reading 'edgesOut')` when there is no `node_modules` to diff against. The job
therefore failed *before* its commit step every time, and the broken lockfile stayed on master. The
tool built for this exact fault had never once completed.

## What was changed

1. **`scripts/lockfile-resolves-every-declared-dependency.test.mjs`** (new) — asks npm ci's
   question without npm and without a network, so it gives the same answer on Windows and on the
   runners: walk every entry in `packages`, resolve each declared `dependencies` /
   `optionalDependencies` name the way node does (nearest `node_modules` first, then up the chain),
   and require both that an entry exists and that its version satisfies the range. Ranges it cannot
   parse **fail** the suite rather than being skipped. A third test names the wasm32 subtree
   explicitly, because the generic check passes the moment *something* resolves.
   It runs automatically: `test.yml` executes every `scripts/*.test.mjs` before the browser install.

   *Proven red before it was trusted green:* against `origin/master`'s own lockfile (`6997a6d`) it
   reports exactly what npm reported — `@tailwindcss/oxide-wasm32-wasi needs @emnapi/core@^1.11.1 —
   no entry anywhere up the node_modules chain` — and exits 1, with no other finding anywhere in the
   lockfile.

2. **`.github/workflows/regen-lock.yml`** — the verification that never worked is replaced by two
   that do: the guard suite above, then a **real `npm ci --ignore-scripts`**. It now repairs
   *in place* first (`npm install --package-lock-only`, which on Linux adds what Windows pruned and
   moves nothing else) and only falls back to deleting and re-resolving the whole lockfile if the
   surgical repair was genuinely not enough — re-floating every dependency on release day is a large
   unreviewed change that can drag in a fresh advisory. A final `npm audit --audit-level=high` makes
   it impossible for this job to push a lockfile that `gate-security` would then refuse.

3. **`package-lock.json`** — regenerated by that workflow, on Linux.

## What this does not change

The two HIGH advisories are still cleared: `sharp` stays `0.35.4` and `js-yaml` `4.3.2`, and
`package.json` is untouched. The three moderates in the vitest dev chain remain below the gate
threshold and are still a separate decision.
